## 構造の違い

### by-claude（段階的）

```
- 段階 1: 基本的な pre-commit フック
- 段階 2: pre-push フックの追加
- 段階 3: 実装例の全体像
- 段階 4: エラーハンドリングの強化
- 段階 5: 環境別の設定
- よくあるカスタマイズ（4パターン：A/B/C/D）
```

**特徴**: 5つの段階を追うことで、段階的に実装を深掘り

### by-gpt（パターン重視）

```
- 最小限の実装
- 推奨実装（当プロジェクト）
- 実装パターン比較（4パターン：1/2/3/4）
- 実行例（正常系・エラー系）
- トラブルシューティング
```

**特徴**: 複数パターンを横並びで比較

## セクション内容の違い

### 段階 1 / 最小限の実装

| by-claude                | by-gpt                 |
| ------------------------ | ---------------------- |
| フォーマットチェックのみ | Lint のみ              |
| コミット実行例を示す     | インストール手順を示す |
| エラー出力を詳細表示     | ファイル構成図を表示   |

**by-claude の実行例**:

```bash
$ git commit -m "feat: new feature"

✖ Code style issues found...
```

**by-gpt の実装**:

```bash
npm install --save-dev husky
npx husky init
```

### 実装パターン

#### by-claude: 5段階 + 4カスタマイズパターン

1. **段階 1-5**: フックを段階的に拡張
   - 段階1: format:check のみ
   - 段階2: pre-push 追加
   - 段階3: 全体像の把握
   - 段階4: エラーハンドリング強化
   - 段階5: 環境別設定

2. **パターン A-D** (最後に紹介)
   - A: lint-staged 最適化
   - B: commitlint 追加
   - C: セキュリティチェック
   - D: CI 連携確認

**学習フロー**: 基礎 → 応用 → カスタマイズ

---

#### by-gpt: 4つの実装パターン横並び比較

| パターン        | 対象   | メリット   | デメリット       |
| --------------- | ------ | ---------- | ---------------- |
| 1. 最小限       | 小規模 | 高速・簡潔 | 検査不十分       |
| 2. 基本（推奨） | 中規模 | バランス良 | 大規模時遅い     |
| 3. 最適化       | 大規模 | 高速       | セットアップ複雑 |
| 4. 強化版       | 本番   | 詳細エラー | スクリプト長い   |

**学習フロー**: パターン選択 → 詳細実装 → 実行例

## コンテンツの特性

### by-claude: 段階的な深堀り

**段階 4: エラーハンドリングの強化**

```bash
#!/bin/sh
. "$(dirname "$0")/_/husky.sh"

echo "🔍 Running format check..."
npm run format:check || {
  echo "❌ Format issues found!"
  echo "💡 Fix with: npm run format"
  exit 1
}
# ... 以下 lint, stylelint も同様
```

**段階 5: 環境別の設定**

```bash
# CI 環境では実行スキップ
if [ "$CI" = "true" ]; then
  echo "⏭️  Skipping pre-commit in CI"
  exit 0
fi
```

**特徴**: 細かい条件分岐やエラーハンドリングを詳述

---

### by-gpt: 実行例の充実度

**正常系**:

```bash
$ git add .
$ git commit -m "feat: add new feature"

[pre-commit]
✓ Prettier check
✓ ESLint check
✓ Stylelint check

[main c4f8a9b] feat: add new feature
```

**エラー系（フォーマット）**:

```bash
$ git commit -m "add code"

[pre-commit]
✖ Prettier check FAILED

husky - pre-commit hook exited with code 1 (failure)

$ npm run format      # 修正
$ git add .
$ git commit -m "add code"  # 再度コミット
```

**特徴**: 実際の実行画面とその解決方法を並べて説明

## カスタマイズ例の違い

### by-claude

**4つのカスタマイズパターン**:

1. **パターン A: lint-staged による最適化**
   - 大規模プロジェクト向け
   - `.lintstagedrc.json` の詳細な説明
   - メリット・デメリット明記

2. **パターン B: コミットメッセージ検証**
   - commitlint 導入
   - conventional commit 例示

3. **パターン C: セキュリティチェック**
   - `npm audit` の追加

4. **パターン D: CI との連携確認**
   - `npm run ci:verify` シミュレーション

**特徴**: **深掘り型**。各パターンを詳細に説明

---

### by-gpt

**カスタマイズなし**。代わりに：

- **パターン比較表** で各方式の得失を明示
- **実行例** で実際の動作を見せる
- **トラブルシューティング** で即対応できる知識提供

**特徴**: **即実践型**。「どのパターンを選ぶか」に注力

## トラブルシューティング

### by-claude

「段階 3: 実装例の全体像」内に簡潔に含める

```bash
# フック確認
ls -la .husky/

# テスト実行
bash .husky/pre-commit
```

**特徴**: セットアップの一部として整理

---

### by-gpt

専門セクション「トラブルシューティング」で詳細記載

| 問題                 | 原因               | 解決方法           |
| -------------------- | ------------------ | ------------------ |
| フックが実行されない | パーミッション不足 | `chmod +x`         |
| Windows 改行コード   | CRLF vs LF         | `.prettierrc` 設定 |
| スキップしたい       | 緊急時の対応       | `--no-verify` 使用 |

**特徴**: よくある質問を先読みして対応

## 使い分けガイド

### by-claude を選ぶべき場合

✅
Husky の仕組みを理解したい ✅ チーム内で段階的に導入したい ✅ 将来的なカスタマイズを視野に入れたい ✅ エラーハンドリングを細かく設定したい ✅ 環境別（CI/ローカル）の条件分岐を知りたい

**読み方**: 序盤から順に追う（段階 1 → 5）

---

### by-gpt を選ぶべき場合

✅ とにかく今すぐ実装したい ✅ 自分のプロジェクト規模に合ったパターンを選びたい ✅ よくあるエラーと対処法を知りたい ✅ 実際の実行画面を見たい ✅ シンプルに保ちたい

**読み方**: パターン比較表から目的を選ぶ → 該当セクション読む（ジャンプ可能）
